# Ротация credentials и отдельная очистка истории

## Состояние после foundation

.env удалён из рабочего состояния и индекса. .gitignore исключает .env/.env.*,
кроме безопасного .env.example. .idea, bytecode и локальные CSV исключены.
**Исторические коммиты и удалённый GitHub не изменены. Ключи не отозваны этой работой.**
Нельзя считать удаление файла ротацией. Все найденные в истории значения считаются
скомпрометированными. Не восстанавливайте их в локальный файл и не вставляйте в чат,
логи, тесты или команды shell.

## Ротация: выполняет владелец аккаунтов

1. Зафиксировать затронутые сервисы без записи значений секретов. Проверить deployment
   environments, Railway/другой хостинг, CI, локальные процессы и активные worker/bot.
   Согласовать короткое окно перехода; при признаках злоупотребления отозвать сразу.
2. **Supabase:** определить тип утёкшего ключа в dashboard. Для отдельного secret key
   выпустить замену и отозвать старый. Для legacy service_role/anon JWT действовать
   по процедуре Supabase для legacy keys/JWT signing secrets: изменение общего JWT
   secret может затронуть другие приложения и токены. Не заменять это одной
   произвольной сменой SUPABASE_KEY. Обновить backend environments, проверить
   фактические grants/RLS и журнал обращений. Привилегированный ключ не должен
   попасть в будущий frontend.
3. **GitHub:** отозвать опубликованный token через настройки владельца, создать
   минимально необходимые permissions и срок действия; обновить GitHub API jobs.
   Проверить доступные логи действий и другие места использования этого token.
4. **Telegram:** отозвать прежний bot token через официальный BotFather, получить
   новый и обновить TELEGRAM_BOT_TOKEN на хостинге; перезапустить единственный
   polling instance. Проверить неизвестные webhook/config изменения, если применимо.
5. **Web3.bio:** отозвать/перевыпустить ключ через кабинет провайдера или поддержку,
   если самостоятельный revoke недоступен; обновить WEB3BIO_API_KEY и проверить usage.
6. Внести **только новые** значения в локальные ignored .env/секреты хостинга.
   Проверить, что старые credentials отозваны средствами провайдера. Выполнить
   минимальные разрешённые smoke checks отдельно от unit-тестов; не логировать headers.
   Не использовать test_supabase_connection.py незаметно: он пишет parser_jobs.
7. Проверить и убрать секреты из логов, artifacts, копий CSV, архивов и старых
   deployments. Сохранить журнал времени ротации и затронутых интеграций без значений.

Источники: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys),
[GitHub: удаление чувствительных данных](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
Рекомендация GitHub: сначала отозвать/ротировать секрет; очистка Git сама по себе
не обезвреживает ранее скопированный credential.

## Очистка Git-истории — НЕ выполнялась

Нужно отдельное разрешение владельца на переписывание истории и публикацию.
Не запускать команды ниже в текущем checkout с незакоммиченными изменениями.

1. Сначала закончить ротацию. Зафиксировать проверенный foundation обычным commit
   отдельно, когда владелец решит публиковать изменения; согласовать freeze с
   участниками и список веток/tags/PR refs. Сделать закрытую контролируемую резервную
   копию незапушенных работ: она тоже содержит потенциальные секреты.
2. Подготовить отдельный свежий clone в защищённой директории. Использовать актуальный
   `git-filter-repo` и инструкцию GitHub; инвентаризировать все старые пути `.env`,
   возможные переименования/копии и другие найденные secret files без вывода значений.
3. Пример **только локального удаления известного пути** в этом отдельном clone:

   ```bash
   git filter-repo --sensitive-data-removal --invert-paths --path .env
   ```

   Если обнаружены другие пути, включить их явно. Это меняет commit IDs. Команда
   не чистит секреты, скопированные в другие файлы: нужен отдельный secret scan.
4. Проверить все refs и sanitized diff, запуск тестов, absence .env/секретов сканером
   с redacted output. Не печатать `git show ...:.env` или обычный diff удаления.
5. **Отдельно согласовать публикацию переписанных refs.** Здесь нет автоматически
   выполняемой force-push команды. Учесть branch protection, открытые PR, signatures,
   форки, внешние clones; координатор должен определить, какие refs обновлять.
6. При необходимости обратиться в GitHub Support для удаления cached/PR views
   согласно их процедуре. Участники получают свежие clones; старый clone нельзя
   просто слить обратно, иначе секреты вернутся. Удаление всех чужих копий гарантировать
   нельзя, поэтому отозванные ключи обязательны даже после очистки истории.

Обычный foundation diff должен исключать `.env`: удалённые строки содержат значения.
В подготовленном review diff файл полностью опущен, его удаление отмечено отдельно.
